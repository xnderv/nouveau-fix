# Неизвестные записи NVIDIA при смене уровня: что о них известно (18.11, до опытов)

Источники (по вертикали — поколения, по горизонтали — открытые материалы):
- envytools rnndb и утилиты nva (класс Г); код nouveau (Г); nvgpu и заголовки open-gpu-kernel-modules — имена NVIDIA
  для Kepler+ (класс Б/Г); записи NVIDIA из базы — 36 чипов от G84 до Pascal, эпохи драйвера по признаку скобки (класс Д);
  образы VBIOS базы (класс В); поиск в интернете.
- Исключён: проект nouveau-dkms (GitHub) — его описание 0x001548 («защёлка DDR3 PHY») по его же словам из декомпиляции
  драйвера NVIDIA 390; по нашим правилам не используется (и противоречит записям: 0x101 идёт на шагах ядра, не памяти).
- Скрипты: scratchpad vert.py / epoch.py / perfb.py / ctx*.py — только чтение, участники обезличены.

| регистр | что это (источник) | по поколениям (база) | вывод |
|---|---|---|---|
| 0x000140 / 0x000144 | NV_PMC_INTR_EN(0/1), бит 0 INTA — разрешение линии прерываний (nvgpu hw_mc, заголовки GM107) | десятки тысяч записей 0/1 во всех записях — так устроен обработчик прерываний; nouveau делает то же (mc/nv04.c) | **к смене частот не относится**; из списка снимается |
| 0x400500 | NV_PGRAPH_GPFIFO_CTL: бит 0 ACCESS, бит 16 SEMAPHORE_ACCESS (nvgpu hw_gr) | тысячи записей во всех записях, большинство не рядом с тактами; nouveau пишет его при сбросе GR и сбросе TLB | **общее управление GR**, не часть смены частот; из списка снимается |
| 0x610300 (GF119+: 0x610700) | PDISPLAY CTRL[0].STATE канала EVO 0 (главный канал дисплея): бит 0 ENABLE — ручная подача команд через MMIO, биты 2–11 METHOD, 31 PENDING (rnndb g80_pdisplay, nva/nvaevo.c) | на время смены уровня бит 0 ставят GT21x, все Fermi, Kepler, Maxwell 1 (поле METHOD — остаток прошлой ручной команды: 0x640/0x600/0x530…); Pascal — нет. При загрузке NVIDIA через этот же регистр подаёт в главный канал команду 0x640 | версия «защита от недогруза» **не следует** из назначения регистра: включение ручного режима, видимо, перехватывает главный канал дисплея — команды из его очереди не выполняются, пока идёт смена частот. Прибор «недогруз» для этого не годится; тест 98 в прежнем виде отменён |
| 0x022680 | в блоке PUNITS/PTOP (0x022400–0x0227ff), адрес не описан нигде; парный 0x022600 читается до записи и показывает прежнее значение | Fermi GF10x/GF11x (кроме GF110, где не пишется): 0x80000000 \| байт 0x0c записи уровня VBIOS (0x1c на нижнем уровне, 0x14 на 07/0f); GF117 и Kepler: всегда 0x80000000 (в VBIOS GF117 байт 0x0c = 0); Maxwell 2 / Pascal — нет. Запись стоит вплотную к чтениям и записям конфигурации PCIe (0x088088 — состояние канала, 0x088150) | значение из VBIOS подтверждено по образам базы (байт 0x0c рядом с байтом скорости PCIe 0x0b). Назначение — вероятно, настройка канала PCIe по уровню (бит 3 только на нижнем уровне). Прибор — состояние и ошибки PCIe, не счётчики застреваний |
| 0x001548 | нет ни в rnndb, ни в nvgpu, ни в заголовках NVIDIA; в Blackwell NV_PBUS_SW_SCRATCH = 0x1400–0x14fc (не тот) | одинаковый протокол с GF108 до Pascal: 0x80000101 / 0x101 — шаги ядра, 0x102 — скрипт памяти, 0x104 — hubk01 (с Maxwell 2 — только 0x101/0x102); бит 31 «идёт»; хост его не читает; в записях GF100 нет | отметка «идёт смена частот» для другого исполнителя — скорее всего программы PMU NVIDIA. У нас на PMU программа nouveau, она её не читает — **запись ничего не даст**; опыт не нужен |
