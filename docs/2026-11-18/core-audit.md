# Аудит ядра 18.11: где драйвер на ключах службы отличается от NVIDIA и что взято не из VBIOS

Ключи — служба после 18.11 (целевой набор + lab_e9e0=2), модуль build-1117i. Код прочитан целиком по пути смены уровня
(clk/base.c nvkm_pstate_prog → nvkm_cstate_prog → gf100_clk_calc / gf100_clk_prog, стадии 0–4, скобка, e9e0).
Сверка с записями NVIDIA — lab/db-core-audit.py (9 чипов Fermi, 45 записей базы + наша + Q0AL; класс Д).

## 1. Совпадает с NVIDIA, значение из VBIOS или по правилу
- Частоты узлов на уровнях, напряжение (карта напряжений VBIOS по speedo), такт дисплея (домен 7, lab_e9e0=2).
- Источник узла — флаг подзаписи уровня VBIOS (1 PLL, 2 делитель). На нашей карте у всех узлов флаг 1 или 2 — правило
  «окно −2…+3 МГц» (флаг 0, эвристика nouveau) не задействовано.
- Пределы PLL — таблица PLL VBIOS; у GPC из равных решений наибольшее M (NVIDIA 304+/390), у остальных — наименьшее.
- Основной делитель GPC — на частоте самого высокого уровня на делителях, ниже — пост-делителем. PMU — делитель к ближайшему.
- Выдержка в скобке — из 0x020130/0x020144 (ставит init-скрипт VBIOS), модель 13.11, запас 0.
- Порядок узлов (подъём 7 8 0 1 2, спуск обратно), XBAR2CLK вместе с памятью, PCIe в конце спуска, PLL не перезапускать,
  пост-делитель хабов до переключателя, пост-делители GPC/hub под скобкой, без бита 0x10 в управлении PLL.

## 2. Постоянные драйвера NVIDIA (в VBIOS их нет и у NVIDIA тоже) — повторены
- Коды замедления на входе в скобку — таблица по чипам (из записей), флаг 0x80, 0x0201a0 = 0x4040.
- Пауза после смены напряжения 195 мкс (NVIDIA ждёт 130–380 по таймеру; своего значения у неё мы не знаем точно).

## 3. Найдено сейчас: отличия, спрятанные в коде
| № | место | у нас | у NVIDIA (база) | на нашей карте |
|---|---|---|---|---|
| 1 | выход из скобки: 0x020160/164 (и 180/1a0) | числа 0 / 0x82 (0 / 0x4040) | на всех 9 чипах — значение, что было до первой скобки (состояние после init-скрипта VBIOS); исключение — часть записей GF108 | совпадает (загрузка: 0 / 0x82 / 0 / 0x4040); на других платах может не совпасть |
| 2 | CTRL_1 (0x020004) в скобке | снимаем 0x68 | снимаются все поставленные младшие биты: 0x28, 0x68, 0xed, 0x128, 0x168 — по плате; на выходе прежнее | совпадает (у нас 0x110068) |
| 3 | ступень перед PLL GPC | 405 (VCO/4) с 03 **и с 07** | с 03 → 405 только GF110 и GF114; **с 07 (810) — сразу на PLL, без ступени, на всех чипах**; GF104/106/108/116/117/119 ступени нет вовсе | **отличается**: каждый подъём 07→0f мы делаем лишнюю запись 810→405 в скобке |
| 4 | делитель GPC, пока GPC на PLL | пишем поле A = 06 (405) | после подъёма делитель не трогает до спуска (13 из 13 на GF114) | отличается после подъёма с 07 (у NVIDIA там 810) |
| 5 | записи NVIDIA, которых у нас нет | — | 0x001548 (отметка «идёт смена тактов» хост↔PMU, вокруг каждой скобки, 8 из 9 чипов); 0x022680 = байт 0x0c записи уровня VBIOS (ключ lab_nv_22680 есть, выключен); 0x610300 бит 0 (ключ есть, выключен); запрет прерываний 0x000140/144; остановка GR 0x400500 (GF114: в 9 из 55 скобок); PXBAR; поле B делителей = делитель самого низкого уровня (lab_nv_divb, выключен); 0x1371c8/cc, 0x139060… при загрузке | не делаем |
| 6 | наше, чего нет у NVIDIA | повтор переключателя и «не снижать напряжение» при застревании (lab_mux_guard); mmu->mutex на время смены | — | действует только при сбое / не меняет регистров |
Мелочь: с lab_nv_hub07mem запись 0x00e9e0 идёт дважды за смену (prog вызывается двумя частями) — тем же значением.

## Что из этого следует
- 1 и 2 — на нашей карте ничего не меняют, но это значения нашей платы, а не правило: правильно — брать состояние до первой
  скобки (как lab_therm=2) и снимать поставленные биты. Можно исправить без опыта на нашей карте (регистры те же).
- 3 и 4 — настоящее отличие поведения на подъёме 07→0f, ровно в том переходе, где у нас были застревания подъёма. Сделать
  «как NVIDIA» = ступень только с 03 и не переписывать делитель на PLL. Нужен опыт (одно отличие за раз).
- 5 — у NVIDIA есть, назначение части неизвестно. 0x022680 — из VBIOS, ключ готов: кандидат на опыт.

## Тест 96 (18.11 16:50–17:23, загрузка 16:49, build-1117j D3C09761)
- Загрузка: выход из скобки по состоянию VBIOS — GPC 0 / 0 / 0x4040, hub 0x82 / 0 / 0x4040 (те же числа, что были в коде);
  маска CTRL_1 0x1ff снимает те же 0x68 (в журнале до/после скобки CTRL_1 0x110068, FSRM — как раньше). Пункты 1 и 2 на
  нашей карте ничего не изменили — как и ожидалось.
- Служебный набор + lab_nv_up07=1 (одно отличие), 1000 подъёмов 07↔0f под нагрузкой (FAST): все 1000 — без ступени 405,
  застреваний подъёма 0, спуска 0, вечных 0, ошибок GPU 0.
**Вывод:** подъём с 07 как у NVIDIA (сразу 810 → PLL, делитель на PLL не трогать) работает; лишняя ступень была не нужна.
Не проверено этим тестом: подъём с 03 (там ступень остаётся, как у NVIDIA GF114) — его покрывает работа под регулятором.

## Тест 97 (18.11 17:31–18:46, build-1117j, служба: набор 18.11 с lab_e9e0=2 и lab_nv_up07=1)
По 600 подъёмов 03 → 0f со спуском 0f → 07 → 03 под нагрузкой (FAST), каждый прогон — одно отличие от службы:
| прогон | записей | застреваний подъёма / спуска / вечных | ошибок GPU |
|---|---|---|---|
| 0. контроль (набор службы) | — | 0 / 0 / 0 | 0 |
| А. lab_nv_22680=1 (0x022680 = байт 0x0c уровня VBIOS: 03 → 0x1c, 07/0f → 0x14) | 1800 | 0 / 0 / 0 | 0 |
| Б. lab_nv_disphold=1 (0x610300 бит 0 на время перехода) | 1800 | 0 / 0 / 0 | 0 |
Контроль: путь через 03 с новым модулем и ключами службы — чисто. Обе записи NVIDIA безвредны, но этот опыт не показывает,
зачем они: счётчики застреваний и ошибок не видят того, на что они действуют. Назначение — отдельными приборами: для 0x610300 —
признак недогруза дисплея после каждого перехода (с битом и без), для 0x022680 — состояние и ошибки канала PCIe.

## Отличие от NVIDIA, отложенное (19.11): темп регулятора
- **Одинаково:** счётчики занятости PMU настроены как у NVIDIA (одни значения на всех Fermi GF104…GF119 по базе; у Kepler
  другие); загрузка = доля «занятых» тактов, от периода замера не зависит.
- **Отличается:**
  - вверх: NVIDIA — через ~0,25 с после начала нагрузки (похоже, прошивка PMU сама сообщает о превышении порога, который
    драйвер передаёт ей после каждого перехода); у нас — опрос раз в 1 с, два замера ≥ 50 % (≈ 2 с), в lab_gov_nv — один;
  - вниз: NVIDIA — по ступени после 4 низких замеров на сетке 2 с (≈ 8 с); у нас 15 с с 0f и 30 с с 07 (в lab_gov_nv — 8 с);
  - пороги: у NVIDIA свои для каждого уровня и счётчика (графика: вверх > 60 %, вниз с 0f < 22 %, с 07 < 6 %; память — свои),
    у нас общие 50 / 15 / 5 % по max(графика, видео), память в решении не участвует;
  - период замера внутри PMU NVIDIA не виден (внутренний таймер закрытой прошивки); наш 100 мс — свой выбор.
- **Как править:** опрос прошивки чаще или сообщение прошивки о превышении порога (наш процесс PERF); пороги по уровням — когда
  будут записи с других карт (одинаковы ли пороги у NVIDIA на разных чипах — по базе не сверено). На стабильность не влияет.

## Наблюдение тестировщика (20.11, sasim44, GT 630 GF108 DDR3, NVIDIA 390.157)
С двумя включёнными мониторами (DVI + HDMI, оба 1920×1080@60) драйвер NVIDIA держит верхний уровень всё время, в любом режиме
PowerMizer; с одним монитором — нормально ходит 0 ↔ 1 ↔ 2 (адаптивный и авто). Похоже на правило NVIDIA: при двух активных
выходах уровень (по крайней мере смена памяти, которой нужна пауза кадра на всех выходах) не меняется. У нас такого правила нет:
регулятор и смена памяти не смотрят на число активных выходов (смена памяти ждёт кадра одного выхода). Для пакета «только ядро»
неважно (память не меняется); для смены памяти — кандидат в правило (проверить по базе: есть ли переходы при двух выходах).
**Сверка по базе (20.11):** в записях Fermi есть 5 с двумя активными выходами дисплея (по регистрам развёртки каждого выхода);
в 4 разборчивых NVIDIA уровни меняет, вместе со скриптами памяти:
- GF108 у3 — оба выхода в одном режиме (934×1904 полных строк×точек), 5 скриптов памяти, 12 смен переключателя;
- GF110 у16 — оба одинаковые (1245×2592), 10 скриптов, 25 смен;
- GF114 у20 — РАЗНЫЕ режимы (1066×1688 и 1111×2080), 2 скрипта, 5 смен;
- GF114 у22 — разные (1125×2200 и 1000×1800), 4 скрипта, 10 смен;
- (GF108 у6 — значения не похожи на развёртку, не учитывается.)
Значит, «при двух мониторах уровень стоит» — не общее правило NVIDIA. У sasim44 два одинаковых 1920×1080@60 (как у у16, где
смены есть), но GF108 DDR3. Ограничение записи: не видно, были ли оба выхода активны именно в момент смены. Версии: зависит от
чипа/типа памяти (DDR3), от длины паузы кадра или от несинхронных выходов — открыто; нужно больше случаев.
**Версия пользователя (20.11): «такт дисплея (домен 7) должен вытянуть оба выхода».** Сверка по базе (частота пикселей —
полная развёртка × 60 Гц, частота кадров в записи не видна — допущение):
| запись | сумма пикселей двух выходов | такт дисплея, который NVIDIA ставила (уровни) | согласие с «такт ≥ суммы» |
|---|---|---|---|
| GF110 у16 | 194 + 194 = 387 МГц | 540 и 405 (0f, 07); 270 (03) — ни разу | да: 270 < 387 — на 03 не опускалась |
| GF114 у22 | 149 + 108 = 257 МГц | 540, затем 270 (03) | да: 270 ≥ 257 — на 03 опустилась |
| GF114 у20 | 108 + 139 = 247 МГц | только 540 (одна запись) | не различает |
| GF108 у3 | 71 + 107 = 178 МГц | только 405 (одна запись) | не различает |
Две разборчивые записи согласны с правилом «такт дисплея уровня ≥ суммы частот пикселей активных выходов». Но у sasim44
(2 × 148,5 = 297 МГц; его домен 7: 270 / 405 / 540) правило разрешало бы 07 (405), а NVIDIA держала верхний уровень — значит,
есть ещё условие (DDR3/память, длина паузы кадра?). Проверка у него: два монитора в меньших режимах (например, оба 1280×720@60,
сумма 148,5 < 270) — если уровни пойдут, дело в нагрузке на дисплей; если нет — в другом.
