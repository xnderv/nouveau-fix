# Аудит ядра 18.11: где драйвер на ключах службы отличается от NVIDIA и что взято не из VBIOS

Ключи — служба после 18.11 (целевой набор + lab_e9e0=2), модуль build-1117i. Код прочитан целиком по пути смены уровня
(clk/base.c nvkm_pstate_prog → nvkm_cstate_prog → gf100_clk_calc / gf100_clk_prog, стадии 0–4, скобка, e9e0).
Сверка с записями NVIDIA — lab/db-core-audit.py (9 чипов Fermi, 45 записей базы + наша + Q0AL; класс Д).

## 1. Совпадает с NVIDIA, значение из VBIOS или по правилу
- Частоты узлов на уровнях, напряжение (карта напряжений VBIOS по speedo), такт дисплея (домен 7, lab_e9e0=2).
- Источник узла — флаг подзаписи уровня VBIOS (1 PLL, 2 делитель). На нашей карте у всех узлов флаг 1 или 2 — правило
  «окно −2…+3 МГц» (флаг 0, эвристика nouveau) не задействовано.
- Пределы PLL — таблица PLL VBIOS; у GPC из равных решений наибольшее M (NVIDIA 304+/390), у остальных — наименьшее.
- Основной делитель GPC — на частоте самого высокого уровня на делителях, ниже — пост-делителем. PMU — делитель к ближайшему.
- Выдержка в скобке — из 0x020130/0x020144 (ставит init-скрипт VBIOS), модель 13.11, запас 0.
- Порядок узлов (подъём 7 8 0 1 2, спуск обратно), XBAR2CLK вместе с памятью, PCIe в конце спуска, PLL не перезапускать,
  пост-делитель хабов до переключателя, пост-делители GPC/hub под скобкой, без бита 0x10 в управлении PLL.

## 2. Постоянные драйвера NVIDIA (в VBIOS их нет и у NVIDIA тоже) — повторены
- Коды замедления на входе в скобку — таблица по чипам (из записей), флаг 0x80, 0x0201a0 = 0x4040.
- Пауза после смены напряжения 195 мкс (NVIDIA ждёт 130–380 по таймеру; своего значения у неё мы не знаем точно).

## 3. Найдено сейчас: отличия, спрятанные в коде
| № | место | у нас | у NVIDIA (база) | на нашей карте |
|---|---|---|---|---|
| 1 | выход из скобки: 0x020160/164 (и 180/1a0) | числа 0 / 0x82 (0 / 0x4040) | на всех 9 чипах — значение, что было до первой скобки (состояние после init-скрипта VBIOS); исключение — часть записей GF108 | совпадает (загрузка: 0 / 0x82 / 0 / 0x4040); на других платах может не совпасть |
| 2 | CTRL_1 (0x020004) в скобке | снимаем 0x68 | снимаются все поставленные младшие биты: 0x28, 0x68, 0xed, 0x128, 0x168 — по плате; на выходе прежнее | совпадает (у нас 0x110068) |
| 3 | ступень перед PLL GPC | 405 (VCO/4) с 03 **и с 07** | с 03 → 405 только GF110 и GF114; **с 07 (810) — сразу на PLL, без ступени, на всех чипах**; GF104/106/108/116/117/119 ступени нет вовсе | **отличается**: каждый подъём 07→0f мы делаем лишнюю запись 810→405 в скобке |
| 4 | делитель GPC, пока GPC на PLL | пишем поле A = 06 (405) | после подъёма делитель не трогает до спуска (13 из 13 на GF114) | отличается после подъёма с 07 (у NVIDIA там 810) |
| 5 | записи NVIDIA, которых у нас нет | — | 0x001548 (отметка «идёт смена тактов» хост↔PMU, вокруг каждой скобки, 8 из 9 чипов); 0x022680 = байт 0x0c записи уровня VBIOS (ключ lab_nv_22680 есть, выключен); 0x610300 бит 0 (ключ есть, выключен); запрет прерываний 0x000140/144; остановка GR 0x400500 (GF114: в 9 из 55 скобок); PXBAR; поле B делителей = делитель самого низкого уровня (lab_nv_divb, выключен); 0x1371c8/cc, 0x139060… при загрузке | не делаем |
| 6 | наше, чего нет у NVIDIA | повтор переключателя и «не снижать напряжение» при застревании (lab_mux_guard); mmu->mutex на время смены | — | действует только при сбое / не меняет регистров |
Мелочь: с lab_nv_hub07mem запись 0x00e9e0 идёт дважды за смену (prog вызывается двумя частями) — тем же значением.

## Что из этого следует
- 1 и 2 — на нашей карте ничего не меняют, но это значения нашей платы, а не правило: правильно — брать состояние до первой
  скобки (как lab_therm=2) и снимать поставленные биты. Можно исправить без опыта на нашей карте (регистры те же).
- 3 и 4 — настоящее отличие поведения на подъёме 07→0f, ровно в том переходе, где у нас были застревания подъёма. Сделать
  «как NVIDIA» = ступень только с 03 и не переписывать делитель на PLL. Нужен опыт (одно отличие за раз).
- 5 — у NVIDIA есть, назначение части неизвестно. 0x022680 — из VBIOS, ключ готов: кандидат на опыт.

## Тест 96 (18.11 16:50–17:23, загрузка 16:49, build-1117j D3C09761)
- Загрузка: выход из скобки по состоянию VBIOS — GPC 0 / 0 / 0x4040, hub 0x82 / 0 / 0x4040 (те же числа, что были в коде);
  маска CTRL_1 0x1ff снимает те же 0x68 (в журнале до/после скобки CTRL_1 0x110068, FSRM — как раньше). Пункты 1 и 2 на
  нашей карте ничего не изменили — как и ожидалось.
- Служебный набор + lab_nv_up07=1 (одно отличие), 1000 подъёмов 07↔0f под нагрузкой (FAST): все 1000 — без ступени 405,
  застреваний подъёма 0, спуска 0, вечных 0, ошибок GPU 0.
**Вывод:** подъём с 07 как у NVIDIA (сразу 810 → PLL, делитель на PLL не трогать) работает; лишняя ступень была не нужна.
Не проверено этим тестом: подъём с 03 (там ступень остаётся, как у NVIDIA GF114) — его покрывает работа под регулятором.
