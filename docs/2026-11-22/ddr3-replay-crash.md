# Сбой повтора памяти DDR3 у sasim44 (GT 630, GF108): разбор (22.11.2026)

**Что было (21.11 16:46, сборка 57e02bc, lab_mem_new=1).** Переход 07 → 0f: драйвер выполнил записанный скрипт A (324 → 896 МГц)
за 16 мс, ret 0 — и в ту же секунду ловушка GR (RT_WIDTH_OVERRUN), запись в несуществующую страницу, канал Xorg убит; чёрный
экран с цветными точками, Reset. Картина «видеопамять на новой частоте отдаёт мусор».

**Повтор — это три слоя приближений:** (1) перевод языка скриптов NVIDIA в memx nouveau (непонятые операции пропускаются);
(2) записи драйвера вокруг скрипта по правилу окна по времени; (3) обстановка и порядок — что делает остальной драйвер вокруг.

**Проверено и отброшено:**
- *Пропуск операции 0x3a* (6 раз в скрипте A, после записи 0x13d834 = 0). В скриптах GDDR5 (GF114, GF106) та же пара — запись
  0x13d8f4 и 0x3a; пропуск там безвреден. Отличие только в адресе; DDR3 тут ни при чём. (Толкование 0x3a из проекта Twilight0 —
  не используем: источник исключён.)
- *Записи «до» и «после»*: записи между загрузкой скрипта в PMU и его пуском (0x132000 = 18000002 → 18000000) в наш список
  попали.
- *Пропуск записи 0x00e104*: это регистр линий GPIO (8 линий по 4 бита, бит 0 — выход); у этой платы линии VID — 5, 6, 7.
  Значения NVIDIA (03: 26200004, 07: 63200004, 0f: 36200004/32200004) — ровно VID 0 / 2 / 4, которые ставит nouveau.
  Напряжение у нас то же.

**Найдено — порядок шины XBAR2CLK и памяти (слой 3).** У NVIDIA (sasim44) скрипт A запущен при XBAR2CLK уже на PLL (1595 МГц),
у нас — при XBAR на делителе 810 (правило lab_nv_hub07mem «XBAR вместе с памятью», взятое из записи нашей GF114): память ушла на
896 при медленной шине и только потом шина поднялась. По всем записям Fermi базы (запуски скриптов памяти на подъёме и спуске):

| чип | подъём | спуск |
|---|---|---|
| GF100, GF104, GF106, GF110, GF114, GF116 (GDDR5) — 45 подъёмов | память, потом XBAR на PLL | XBAR с PLL, потом память |
| GF119 (DDR3) — 13 / 11 | так же | так же |
| **GF108** (5 плат, DDR3 и GDDR5), **GF117** (28-нм вариант GF108, DDR3) | **XBAR на PLL, потом память** | **память, потом XBAR** |

Решает семейство чипа, не тип памяти. Из VBIOS не выводится (у GF117 подвыбор хаба 0) — постоянная драйвера NVIDIA по чипу,
как коды скобки. В драйвере (build-1122d): lab_nv_xbarmem (−1 по чипу: GF108/GF117 — шина снаружи; 0 — память снаружи;
1 — шина снаружи). На нашей GF114 поведение не меняется.

**Решение (22.11, build-1122e):** порядок «шина снаружи памяти» — для ВСЕХ чипов (lab_nv_xbarmem=1 по умолчанию). Это
безопасное направление: пока меняется память, шина уже или ещё быстрая. На GF114 и GF106 он проверен (октябрь; тест 28 — «порядок
не критичен»; тест 69 шаг 0; прогон 4 rox4d), на GF108/GF117 так делает NVIDIA. Порядок NVIDIA остальных чипов — ключ 0.
Принцип: предохранитель с понятной причиной, не влияющий на производительность, оставляем для всех.

**Дальше:** проверить на нашей карте, что ничего не изменилось; сборка sasim44 с этим порядком и повтор lab_mem_new=1.
Если сбой останется — следующие кандидаты: операции 0x3a / 0x34 0x0b, ожидание кадра второй головы (0x14 с аргументом 0x10000).

**Поправка 24.11.** Порядок шины и памяти — факт поведения NVIDIA на GF108 и разумный предохранитель, но причиной сбоя он не
подтвердился: после исправления порядка (сборка da6fa2c) память на 896 МГц по-прежнему отдаёт неверные данные — у sasim44
(зависание экрана) и на ноутбуке GT 630M без экрана (порча данных без зависания, 324 МГц на PLL — чисто). Следующий кандидат —
пропущенные ожидания после строба 0x13d834 (оп 0x3a): docs/2026-11-24/seq-ops.md.
