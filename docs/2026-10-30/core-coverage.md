# Карта покрытия: управление частотой ядра Fermi (без памяти) — 30.10.2026

Вселенная та же, что в `docs/model/coverage.md` (записи NVIDIA 390 при смене уровня на нашей GTX 560 Ti), но только ядро:
такты 0x137000–0x1373ff без тактов памяти (0x137300–0x1373f8 и 0x137360, 0x1373c0 отнесены к памяти: первые пишутся
вместе со скриптами памяти, 0x1373c0 — счётчик частоты, для переключения не нужен), скобка PTHERM, напряжение (GPIO),
хост-домен, PCIe. Скрипты памяти, PMU и контроллер памяти сюда не входят.

|---|---|---|---|---|---|

| 3. скобка замедления: вход | 0x020160/180/1a0 (+4 для хаба), 0x020004 | да | да | **все 7** | коды по чипу (таблица из 43 трасс) |

| 9. хост-домен | 0x00e9e0 | ключом | вывод | нет (тест 10: не причина зависаний) | таблица VBIOS (подзапись 7) |
| 10. PCIe gen1 ↔ gen2 | 0x02241c, 0x022680 | да (в конце спуска, как NVIDIA) | вывод | нет | семейство / таблица |

Что проверено опытом и почему это важно:
- **скобка** — без неё GR зависает (7 из 7, 23.10; 63б, 64б); спасает само замедление (Е18, 64а без битов CTRL_1 — чисто);
  держать его после записи переключателя не нужно (Е20, 0 на 200);
- **ожидание** — нужно только в «плохих» сессиях (тест 57); в хороших переключение терпит и 0 (тест 62, до 1 нс);
  кандидат для ядра Linux (8 / 4,5 мкс, как NVIDIA) — 0 застреваний на 3000 подъёмах (тест 65а);
- **делитель ядра 0x1371d0** — запись со сменой значения перед переключателем лечит застревание (тест 53);
- **пост-делители GPC и hubk06** — путь NVIDIA (GPC /8 к 810 на низком уровне, hubk06 под скобкой; тесты 19, 22–24).

## Сверка регистров ядра с записями NVIDIA на 9 чипах

Выводы: источники делителей — действительно общие для Fermi, кроме GF108 (у него своё дерево тактов); скобка — своя у
каждого чипа (это известно, таблица кодов есть); «семейная» метка у управления PLL (0x137000 и др.) не подтвердилась даже
на других GF114 — сравнение «набор значений» тут слишком грубое (в управлении PLL идёт последовательность битов: захват,
синхронный режим), нужна сверка по переходам.

## Ожидание в скобке: откуда 8 и 4 мкс
**Из VBIOS мы его пока не берём.** Сейчас это таблица по группам плат, где группа определяется значением 0x020130,
которое пишет devinit VBIOS:
| 0x020130 | платы | замедление GPC / hub | ожидание GPC / hub |
|---|---|---|---|
| 8107040a | GF100, GF110, GF114 (настольные) | /6, /2 (GF114, GF110 1086); /2 (GF110 1080); /8, /8 (GF100) | **8 / 4 мкс** при /6 и /2; 4–5 мкс при /2; GF100 не измерено |
| 8107030a | настольные GF104, GF106, GF108 | /2, /2 | ~18 мкс (GF106) |
| 8107060c | мобильные GF106M, GF108M, GF114M, GF119M | /8 (GF108M) | ~150 мкс |

Что говорит за связь с VBIOS: NVIDIA читает 0x020130 (и на GF114 ещё 0x020144 = 0x20080) **прямо перед** ожиданием, в
каждой скобке; одна и та же микросхема в разных группах ждёт по-разному (GF114 1200 и 1211, GF108 0de1 и 0df4).
Что уже отброшено: «ожидание = время плавного замедления ступенями» (поля grad_enable и slowdown_factor_extended в
0x020130 по nvgpu) — 28.10 регистры ступеней 0x0202c0–c8 и 0x0203c0 на нашей карте читаются нулями, и замедление
включается сразу (признак за ~2,2 мкс); «байт 0x020130 + 1 мкс» — опровергнуто записью GF106 (27.10).
Что видно по числам: внутри группы 040a ожидание растёт с глубиной замедления — /2 → 4 мкс (хаб; GPC у GF110 1080),
/6 → 8 мкс (GPC). Обе точки ложатся на «делитель + 2 мкс», но двух точек мало; проверить можно по записям GF100
(/8 — предсказание 10 мкс), если в них достаточно частые чтения таймера. Похоже на правило в самом драйвере NVIDIA,
а не на свойство железа.
Решающая проверка связи с VBIOS — опыт Е17: на стенде записи поменять 0x020130 (040a → 030a) до загрузки NVIDIA 390 и
посмотреть, станет ли ожидание ~18 мкс. Если да — ожидание считается из значения, которое ставит VBIOS, и кода
замедления; если нет — это таблица по чипам внутри драйвера NVIDIA, и нам остаётся такая же таблица.

## Насколько наш драйвер может посчитать переключение ядра для другой карты Fermi
Для ядра «скриптов» нет (в отличие от памяти, где PMU исполняет скрипты): последовательность записей хоста драйвер
считает сам — частоты уровней из таблиц VBIOS, коэффициенты PLL и делители по формуле (код nouveau + наш путь NVIDIA),
напряжение из таблицы VBIOS, коды замедления и ожидание — из наших таблиц по чипам и группам.

| что | для другой платы Fermi | проверено |
|---|---|---|
| частоты уровней, напряжение | из её VBIOS — да | GF114 (наша), GF106 (rox4d) |
| PLL и делители | по формуле — да | GF114 живьём, GF106 один раз |
| источники делителей | константы Fermi — да (кроме GF108) | 9 чипов по записям |
| коды замедления в скобке | таблица по чипу — есть для 8 чипов; у GF110 зависят от платы | записи NVIDIA |
| ожидание в скобке | таблица по группам — есть для трёх групп, формулы нет | GF114 точно; GF106, мобильные — по записям |
| GF117 / GF119 | у части плат скобки нет вовсе — путь не изучен | — |

Оценка: на настольных Fermi из известных групп драйвер может посчитать переключение ядра почти целиком (кроме GF117/GF119
и выбора кода у GF110). **Живьём это подтверждено на двух чипах из девяти** (GF114 — тысячи раз, GF106 — один подъём).
Следующий шаг, который превратит оценку в число: генератор переключения ядра по VBIOS (как memgen2 для памяти) —
по VBIOS каждой платы из базы предсказать записи ядра на каждом переходе и сравнить с её записью NVIDIA. VBIOS и записи
этих 43 карт у нас уже скачаны.

## VBIOS плат с записями NVIDIA (30.10, lab/trace-vbios.py)
Уточнение к «VBIOS и записи этих карт у нас уже скачаны»: из 33 плат Fermi с записями NVIDIA у 29 образ VBIOS лежит в
базе рядом с записью. У четырёх его нет; драйвер NVIDIA при старте сам читает VBIOS, и у двух из них образ собран из
чтений в записи (класс В):
| плата | чип, PCI id | откуда образ | версия |
|---|---|---|---|
| у2 | GF100, GTX 480, плата 3842:1482 | собран из чтений PROM | 70.00.21.00.82 |
| у3 | GF108M, GT 425M (ноутбук), 1028:0468 | собран из копии в видеопамяти | 70.08.19.00.10 |
| у7 | GF108M, GT 620M…640M LE (ноутбук), 1043:2114 | в записи нет (VBIOS из ACPI) | — |
| у26 | GF117M, GT 620M (ноутбук), 1025:064a | в записи нет (VBIOS из ACPI) | — |

Проверка метода на платах, у которых образ в базе есть: из PROM — побайтно тот же образ (GF100 у1, 0 различий); копия из
видеопамяти — та же версия, но 32–36 байт другие (VBIOS правит свою копию при старте; GF108 у5, у1). Образ у3 поэтому —
копия после старта, а не дамп ПЗУ: таблицы читать можно, но 30–40 байт могут отличаться от ПЗУ. Образы — вне
репозитория (`~/Home/nouveau-archive/trace-vbios/2026-10-30-fermi/` + manifest.csv с SHA256). Без образа остались только
две ноутбучные платы (их VBIOS приходит из ACPI); на TechPowerUp их нет (поиск 30.10, provenance.md).
