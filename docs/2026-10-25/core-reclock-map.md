## 0. Коротко

1. **Такт ядра собирается из одного кварца 27 МГц.** Генератор SPPLL даёт 1620 МГц, от него питаются делители и PLL узлов.
   Каждый узел через переключатель (мультиплексор 0x137100) берёт такт либо с делителя, либо со своего PLL.
2. **Уровни 03 и 07 NVIDIA строит целиком на делителях 1620 / n**, PLL — только на 0f, где делителю не хватает.
   - nouveau выбирал «что ближе к числу таблицы», а таблица хранит целые мегагерцы. Отсюда PLL на уровне 03 и PMU на 216 МГц.
   - Исправлено, **проверено**.
3. **Любая смена такта GPC и hubk06 у NVIDIA идёт внутри «скобки» замедлителя PTHERM FSRM.** Без скобки под нагрузкой GR
   зависает (7 из 7), со скобкой — нет. **Проверено.**
4. **Переход устроен как стек.** Напряжение и PCIe поднимаются первыми и опускаются последними, спуск — это подъём
   наоборот. **Видно**, проверено частично.
5. **В части загрузок переключатель ядра застревает при уходе с PLL на делитель** — примерно на 1 % спусков 0f → 07.
   - Лечит «команда»: запись делителя ядра с новым значением внутри скобки прямо перед переключателем, как у NVIDIA.
   - **Проверено в одной плохой сессии:** 0 тайм-аутов на 2700 подъёмов против 27 на 2279 без команды.
   - Почему это помогает — не знаем.
6. **Новое при составлении карты (гипотеза): у NVIDIA, похоже, общее правило «цель готовится в последний момент».**
   - То, на что узел сейчас переключится (делитель или PLL), NVIDIA настраивает или перезапускает внутри скобки,
     непосредственно перед переключателем.
   - nouveau готовит цели заранее, отдельными стадиями по всем узлам.
   - Единственный отказ, оставшийся после скобки и делителей, — ровно там, где цель «залежалась»: делитель ядра, который
     простаивал весь уровень 0f. Раздел 4.2.
7. **Решения о смене уровня у NVIDIA:** прошивка PMU считает загрузку, решает драйвер.
   - Вверх — сразу на 0f, по событию.
   - Вниз — по одной ступени, после 8 с низкой нагрузки.
   - Пороги свои для каждого уровня.
   - **Видно** в записях. Наш регулятор похож по форме.
8. **Что из этого свойство чипа, а что — платы,** без данных с других карт не сказать (раздел 9).
9. **Открытый код самой NVIDIA для Tegra (gk20a, gm20b) — тот же блок тактов** по тем же адресам 0x137000 / 0x137100 /
   0x137250. В его комментариях прямо записаны правила, которые мы вывели из трасс: «разбить скачок частоты пополам перед
   уходом с PLL», «PLL — в обход, прежде чем выключать», «второй намеренный запуск делителя, чтобы он делил правильно»,
   2 мкс между делителем и переключателем. Раздел 14.

## 1. Дерево тактов ядра

```
кварц 27 МГц
 └─ SPPLL0: 27 × 60 = 1620 МГц (0xe800; ставит VBIOS, ни nouveau, ни NVIDIA его не пишут)
     ├─ делитель опоры 0x137140 + i·4 → 405 МГц ─► PLL узла 0x137000 + i·0x20 ───────────────┐  (GPC: 405 × 40 / 9 = 1800)
     ├─ основной делитель 0x1371d0 + i·4 (есть только у GPC, ROP, hubk07) ─────────────────────┤
     │     поле A (биты 0–5): деление (A + 2) / 2, A = 02 → 810, 06 → 405, 1e → 101,25          ├─► переключатель 0x137100
     └─ у hubk06 и hubk01 основного делителя нет: 1620 идёт на переключатель напрямую ─────────┘   (бит на узел, 1 = PLL)
                                                                                                    └─► пост-делитель 0x137250 + i·4 ─► узел
 └─ SPPLL1 1620 (0xe820) ─► делители памяти (вторая дорожка: поле B, бит 8 источника) → 135 / 324;  REFPLL → MPLL → 2004
```

Узлы (номер idx как в nouveau):
- 0 — GPC: шейдеры, ядро — половина его частоты;
- 1 — ROP;
- 2 — hubk07;
- 7 — hubk06;
- 8 — hubk01;
- 9 — copy;
- 0xc — PMU;
- 0xe — vdec;
- хост-домен — 0x00e9e0.

| Элемент | Что знаем | Уверенность | Общность |
|---|---|---|---|
| SPPLL0 / SPPLL1 | 1620 МГц от кварца. В записях NVIDIA только читает (1021 чтение в t1/t2), значение не меняется. Общий источник обоих входов переключателя ядра | видно | чип (эталонная GTX 560 работает ровно на 1620 — 810 / 1620) |
| Основной делитель | Действует поле A. Поле B — вторая дорожка (SPPLL1 + поле B) при бите 8 источника 0x137160. У ядра бит 8 всегда 0, так что поле B ядра не действует | видно; «поле B ни при чём» для тайм-аутов — проверено (тесты 53, 55, 56) | чип? |
| Делитель опоры → 405 | Питает PLL узлов. У GPC его ставит VBIOS, при переходах его не пишет ни NVIDIA, ни nouveau. У ROP / hubk07 NVIDIA при подъёме пишет опору (0x137144 = 0x81200606) | видно | чип? |
| PLL узла | Бит 0 — включение, 2 — синхронный режим, 17 — захват. Бит 4 («проверка захвата») NVIDIA не ставит. У nouveau бит 0x10 после захвата переводил узел в обход (ядро шло на ~25 МГц) — исправлено 20–22.10 (`lab_gpc_seq`) | проверено | Fermi? |
| Переключатель 0x137100 | Чтение показывает фактическое положение: если переключение не прошло, бит остаётся | проверено (тест 21, все тайм-ауты) | Fermi |
| Пост-делитель | Делит после переключателя. На 03 у GPC — /8 (0e): 810 / 8 = 101,25 | видно, проверено (тест 22) | чип |
| Замедлитель FSRM (PTHERM) | Не часть дерева, но замедляет такт домена: FSRM0 — GPC, FSRM1 — hubk06. Раздел 5 | проверено | чип? |

**Чего не знаем:**
- что именно тактируют hubk07, hubk06 и hubk01;
- выключается ли выход простаивающего делителя ядра, пока ядро на PLL (для раздела 4 это главный вопрос);
- работает ли у делителя что-то вроде «перезапуска счёта» при записи нового значения.

## 2. Уровни и выбор источника

| Узел | 03 | 07 | 0f |
|---|---|---|---|

| ROP, hubk07 | делитель 270 | 810 | PLL 1909,3 |
| hubk06 | пост-делитель 270 | 810 | PLL 1645,3 (от BIOS, = эталон 560 Ti) |
| PMU | 202,5 (BIOS, NVIDIA не пишет) | 202,5 | 202,5 |

### 2.1. На 03 и 07 — делители на сетке 1620 / n, PLL только на 0f
- **Что видно:** на 03 и 07 переключатель = 0, все узлы на делителях. На 0f — 0x187.
- **Почему так (гипотеза):**
  - делитель не надо захватывать;
  - он даёт точную долю частоты и одинаков на любом экземпляре чипа;
  - смена делителя — одна запись без ожидания.

  PLL надо захватывать, он вносит дрожание и ест энергию, поэтому он нужен только там, где делителю не хватает.
- **Почему не иначе (проверено).** nouveau ставил GPC на уровне 03 на PLL 100,894 МГц: он на 144 кГц ближе к «101» из
  таблицы, чем делитель.
  - Уход с этого PLL на 03 → 07 под скобкой отказывал: 3 тайм-аута на 54 подъёма и 2 зависания (тесты 18, 19, 21).
  - С делителем, как у NVIDIA (`lab_gpc_div=1`), — 180 подъёмов из 180 чисто (тест 22, его повтор, тест 23).
- **Общность.** Правило NVIDIA драйверное — вероятно, **Fermi**. А вот получится ли у nouveau PLL на 03, зависит от чисел
  VBIOS (**плата**): если частота 03 делится нацело, ошибки нет.

### 2.2. Таблица VBIOS хранит целые мегагерцы — корень двух ошибок nouveau
- **Что видно:** 101 = 101,25; 203 = 202,5; 1645 = 1645,3. nouveau читает 14 бит частоты и принимает число за точную цель
  в кГц.
- **Вывод (расчёт):** правило nouveau для поколения до Fermi (gt215) даёт ровно выбор NVIDIA на всех узлах. Правило такое:
  - делитель, если он попал в окно −2…+3 МГц от таблицы;
  - частота не выше цели.

  В gf100 и gk104 его заменили на «ближе любой ценой».
- **Что сделано:** `lab_gpc_div` и `lab_pmu_div` — это частные случаи правила gt215.
  - Тест 23: PMU на 202,5 ничего не ломает.
  - Это исправление «как у NVIDIA», а не лекарство от зависаний — связи с зависаниями не доказано.
  - Общее правило для upstream не написано и не проверено.
- **Общность:** правило — **Fermi** и, возможно, Kepler (gk104 — тот же код). Какие числа округлены — **плата**.

### 2.3. Флаги в таблице VBIOS
- **Что видно.** Флаги ровно разделяют штатные 03 / 07 и разгонный 0f:
  - старшие биты 14–15 частоты узла: 2 на 03 / 07, 1 на 0f;
  - байт 1 записи уровня: 0x40 на 03 / 07, 0 на 0f.

  nouveau эти биты отбрасывает.
- **Смысл не доказан, есть два толкования:**
  - «частота из сетки делителей / точная, нужен PLL»;
  - «базовый / разгонный уровень».
- **Общность:** ?. Различить толкования можно только по таблицам других карт (раздел 9).
- **30.10, плата Q0AL (GF114, EVGA):** hubk06 на 0f = 1620, делитель попадает ровно, арифметические правила (окно GT215,
  «ближе» gf100) выбирают делитель, NVIDIA — PLL. Флаг 1 объясняет выбор на обеих платах; толкования флага между собой
  эта плата не различает. Подробно: docs/2026-10-30/q0al-core-check.md.

### 2.4. Поле B основного делителя = делитель уровня 03
- **Что видно:** у NVIDIA в неактивном поле всегда делитель уровня 03 (ядро 1e, ROP / hubk07 0a, память 16). nouveau пишет
  оба поля одинаково.
- **Проверено:** на тайм-ауты поле B не влияет (тест 53, а также 55в и 56в с командой).
- **Кто и когда его использует — не видно** (может быть, аварийный такт). Общность: ?.

## 3. Один переход по шагам

### 3.1. NVIDIA — стек
Подъём 03 → 0f (запись try7, 296,05 с; спуск — те же шаги в обратном порядке):
1. Энергосбережение контроллера памяти выключено, дисплей 0x610300 бит 0, кросс-бар PXBAR в «переходное».
2. Напряжение вверх, затем ~0,2 мс выдержки по таймеру карты.
3. PCIe → 5 ГТ/с.
4. hubk06 → PLL (скобка), hubk01, copy.
5. GPC: скобка → путь делителя на 405 → перезапуск PLL → переключатель → снять скобку.
6. ROP → PLL (без скобки).
7. Память: скрипт прошивки PMU (~10 мс).
8. vdec, хост-домен, hubk07 → PLL.
9. Дисплей и PXBAR обратно. Прошивке PMU отправляются пороги регулятора для нового уровня.

- **Почему так (гипотеза):** что поднято последним, снимается первым. Тогда в любой момент перехода каждый узел работает в
  окружении, в котором уже работал на одном из двух уровней. Промежуточных сочетаний, которых нет ни на одном уровне, не
  бывает.
- **Почему не иначе — на нашей карте почти не важно.** Ключи порядка поодиночке зависаний не убирали и не вызывали:
  - `lab_order` (тесты 12, 34а);
  - `lab_nv_hub07mem` (тест 28);
  - `lab_nv_pcie_late` (тест 27);
  - `lab_nv_hubpost` (тест 26).

  Насколько видно, порядок — запас прочности, а не условие. **Проверено частично**, по одному прогону на ключ.

### 3.2. nouveau (upstream)
- **Порядок перехода:** PCIe → память → напряжение вверх (если нужно) → такты ядра стадиями по всем узлам → напряжение вниз.
- **Стадии ядра:**
  - 0 — делители (только узлам, у которых цель — делитель);
  - 1 — все узлы на делитель (переключатель);
  - 2 — PLL: выключить, запрограммировать, ждать захват — вне всякой скобки;
  - 3 — узлы с целью PLL переключаются на него;
  - 4 — пост-делители.
- **На Fermi смена частот в upstream выключена** (`allow_reclock = false`). Поэтому ошибки этого кода почти никто не видел.

## 4. Переключатель источника — главное место

### 4.1. Что NVIDIA делает вокруг каждого переключения GPC (видно, записи t1, try3, try7)
- **Подъём 07 → 0f.** Скобка → выдержка ~8 мкс → делитель A 02 → 06 (путь делителя 810 → 405) → коэффициенты PLL →
  PLL выкл → вкл → захват (виден через ~8 мкс) → переключатель → снять скобку.
- **Подъём 03 → 0f.** Скобка → пост-делитель 0e → 02 (101,25 → 405) → PLL выкл → вкл → переключатель → снять скобку.
  Коэффициенты не пишутся: они остались с прошлого раза.
- **Спуск 0f → 07.** Скобка → выдержка → делитель A 06 → 02 за ~2 мкс до переключателя → переключатель → сразу снять
  скобку → подтверждение чтением через ~56 мкс, уже без замедления. PLL GPC остаётся включённым.
- **hubk06 на спуске:** пост-делитель — до переключателя, в той же скобке.

### 4.2. Правило «цель — в последний момент» (гипотеза, новое)
И на подъёме, и на спуске NVIDIA готовит источник, на который узел сейчас перейдёт, внутри скобки, непосредственно перед
записью в переключатель:
- на подъёме цель — PLL. NVIDIA выключает и снова включает его в скобке, за ~10 мкс до переключателя, хотя он уже стоял
  включённым и захваченным;
- на спуске цель — делитель. NVIDIA пишет его новым значением за ~2 мкс до переключателя.

У nouveau цели готовятся заранее и для всех узлов сразу:
- делители — на стадии 0, до скобки и тем же значением, что уже стоит;
- PLL — на стадии 2, вне скобки.

**Что с этим согласуется:**
1. **Все 34 тайм-аута с подробной записью** (25.10; 13 более ранних 24.10 — тоже GPC) — у GPC (idx 00) и только при уходе с PLL на делитель. Это ровно тот
   случай, где цель у nouveau «залежалась»: делитель ядра простаивает весь 0f и перед переключением переписывается тем же
   значением (в журнале «0x1371d0 81200202 -> 81200202»).
2. **На подъёме цель у nouveau — PLL**, который выключается на спуске и заново захватывается на каждом подъёме, то есть он
   «свежий». Тайм-аутов делитель → PLL после ранней сборки 20.10 — по одному в двух загрузках 24.10.
3. **Команда** — свежий делитель прямо перед переключателем — убрала тайм-ауты в плохой сессии (0 на 2700).
4. **ROP и hubk07** тоже уходят с PLL на «залежалый» делитель, но без скобки, и не застряли ни разу.
5. **hubk06** уходит со скобкой, но его делительный путь — сам SPPLL, который никогда не простаивает. Тоже ни разу.

**Уточнённая гипотеза:** застревание бывает, когда сходятся три условия:
- скобка FSRM;
- переход на источник, который простаивал;
- плохая загрузка.

Хватит любого из лекарств: свежая цель (команда) или, возможно, отсутствие скобки — это не проверено, опыт Е5.

**Чем опровергнуть:** опыты Е1–Е5 (раздел 11). Например, если «то же значение прямо перед переключателем» лечит так же, как
новое — дело во времени записи, а не в смене значения. Если `lab_pll_keep` (PLL не перезапускается) вызовет тайм-ауты на
подъёме — правило касается и PLL.

**Почему NVIDIA так делает, мы не знаем.** Возможно, это не задуманное лекарство, а побочный эффект её порядка «всё для узла —
в одной скобке». Смена 06 → 02 на спуске нужна NVIDIA просто потому, что на подъёме она поставила 06 — правило «405 перед PLL».

### 4.3. Тайм-аут в плохих загрузках — факты
- **Где.** Только GPC, только PLL → делитель. Сейчас это 0f → 07. До `lab_gpc_div` было ещё 03 → 07, с PLL уровня 03.
- **Загрузка плохая или хорошая целиком.**
  - Плохие (там, где переключений хватило для вывода): 24.10 00:43, 02:17, 03:00, 11:56, 15:35; 25.10 06:32, 12:30, 12:45,
    14:05, 18:40 — 10 загрузок.
  - Хорошие: 24.10 17:26 (0 на 3178) и 25.10 14:47 (0 на 2400 без команды). **2 из 12** — оценка по малому числу загрузок,
    прежняя цифра «четверть хороших» — тоже.
- **Частота в плохой загрузке** — 0,5–1,2 % спусков. Внутри сессии отказы, похоже, независимы, пачек нет: 25.10 18:40 близких
  пар было столько же, сколько при случайном раскладе (2 промежутка ≤ 8 подъёмов из 17 при ожидании ~2).
- **Время жизни застревания: не меньше ~60 мс и не больше ~0,33 с.**
  - Три повтора защиты по 20 мс не помогли ни разу: сегодня 81 повтор из 81.
  - Следующий переход 07 → 03 через 0,33 с всякий раз уходил на делитель сразу. В медленном режиме 25.10 06:32 — через ~4 с,
    тоже сразу.
- **Регистры одинаковые.** У плохих и хороших загрузок одинаковы 126 регистров снимка. В момент тайм-аута PLL захвачен,
  делитель включён, скобка стоит как положено (FSRM `0002000a`, CTRL_1 `00110000`).
- **До скобки — ни одного тайм-аута.**
  - С 20.10 до 24.10 00:43: 40 загрузок, ~1600 уходов с PLL на делитель. Если бы плохими были те же ~5 загрузок из 6,
    ждали бы около 10.
  - Без скобки на 03 ↔ 07 (тест 20) и за неделю жизни с регулятором — тоже ни одного.
  - Значит, **вероятно, скобка — необходимое условие** (**видно**, не проверено: сборки тогда были другие).
- **Исключено** (**опровергнуто**):
  - число переключений, время на 0f и внизу, режим теста, сборка;
  - порядок «скобка — переключатель» (тест 48: замедление уже снято, всё равно застрял);
  - температура (тайм-ауты при 55–77 °C);
  - видеодвижок;
  - поле B (тест 53);
  - «толчки» делителя (3 толчка ÷5 в хорошей сессии ничего не испортили);
  - «запись перезапускает счётчик в случайный момент» (50а: команда в хорошей сессии ничего не испортила).
- **Лечение — команда.** Она действует на каждом переключении, но сессию не чинит: стоит её убрать — тайм-ауты возвращаются
  (55б, 56б).
- **Где живёт плохое состояние — неизвестно.** Не в регистрах делителя ядра. Кандидаты: делитель опоры, PLL, сам
  переключатель, что-то вне дерева тактов (PTHERM, PMU, опорная частота PCIe).

### 4.4. Защита (`lab_mux_guard`)
- **Зачем.** nouveau после тайм-аута идёт дальше: выключает PLL и снижает напряжение, хотя узел ещё на нём.
  - Без `lab_pll_keep` обходилось: выключенный PLL, видимо, «отпускает» переключатель.
  - С `lab_pll_keep` вышло зависание 34б: GPC 1800 МГц при 0,95 В.
- **Что делает:** 3 повтора, потом PLL и напряжение не трогаются до следующего перехода.
- **Проверено:** 25.10 — 2 тайм-аута утром и 27 вечером, ни одного зависания.
- Это ошибка upstream № 1 (раздел 8).

## 5. Скобка замедлителя FSRM
- **Что видно.** На время смены такта GPC или hubk06:
  - NVIDIA пишет FSRM_2/3/4 домена (код 0xa у GPC, 0x2 у hubk06);
  - снимает тепловые входы (CTRL_1 0x110068 → 0x110000);
  - ждёт по таймеру ~8 мкс у GPC и 4–5 мкс у hubk06;
  - делает изменение и снимает скобку.

  Признак FSRM_STATUS NVIDIA не читает. Мы ждём признак (бит 17 и записанный код), он наступает через ~2,1 мкс. «Пустые»
  скобки, без изменений внутри, у NVIDIA тоже бывают.
- **Почему так (гипотеза).** В момент смены источника узел может получить укороченный или неровный такт: замедленная логика
  его переносит. Тепловые входы снимаются, чтобы аппаратное замедление не вмешалось посреди переключения.
- **Почему не иначе (проверено):**
  - без скобки на 07 ↔ 0f под нагрузкой GR завис 7 раз из 7 (23.10), со скобкой — 300+ чистых подъёмов;
  - скобка без ожидания (тест 14) зависла;
  - по признаку чисто (тесты 16, 17 и все последующие).
- **Скобка и тайм-аут.** Все тайм-ауты — со скобкой (раздел 4.3). ROP и hubk07 без скобки не застревают.
- **Общность.** Коды и времена — чип?. Нужна ли скобка на других картах — ?.

## 6. Напряжение, PCIe, память — в переходе (коротко)
- **Напряжение** — первым вверх, последним вниз (`lab_volt_first`, в базе).
  - После каждой смены NVIDIA выжидает ~195 мкс по таймеру: от регулятора платы обратной связи нет (**видно**).
  - У нас выдержки нет. Ключ `lab_volt_wait_us` проверялся одним прогоном (тест 32), для вывода этого мало.
- **PCIe** — у NVIDIA 5 ГТ/с первым вверх и 2,5 последним вниз. У нас вниз в начале перехода (ежедневная) или в конце
  (тестовая база).
- **Память** — отдельный домен, её меняет прошивка PMU скриптом (слова NVIDIA, через memx).
  - Подъём — после ядра, спуск — до ядра (`lab_mem_order`).
  - Скрипты — **плата**. Генератор по таблицам VBIOS — отдельная работа
    ([memory-scripts-vs-nouveau.md](../2026-10-24/memory-scripts-vs-nouveau.md)).
- **Есть у NVIDIA, нет у нас:** энергосбережение контроллера памяти, удержание дисплея 0x610300, PXBAR, 0x001548.
  Насколько видно, на стабильность они не влияют (**видно**, не проверено). У нас контроллер памяти всегда в безопасном
  положении «выключено» (тест Б 24.10).

## 7. Кто решает: регулятор
- **NVIDIA** (**видно**, запись try7):
  - хост при загрузке настраивает счётчики занятости в PMU, прошивка считает;
  - вверх — сразу на 0f, через ~0,25 с после появления нагрузки, по событию (подъёма 03 → 07 нет ни разу);
  - вниз — по ступени, через 8 с на каждую, на сетке 2 с;
  - после каждого перехода хост отдаёт PMU пары порогов под новый уровень. Наше толкование для графики: вверх при > 60 %,
    вниз с 0f при < 22 %, с 07 — при < 6 % (**гипотеза**).
- **Почему так (гипотеза).** Вверх быстро — результат нужен сейчас. Вниз медленно — ошибочный спуск даёт заметный провал, а
  лишние 8 с стоят немного энергии. Пороги под уровень — это гистерезис.
- **У нас** (`lab_gov=2`): считает наш процесс PERF в прошивке PMU, решает драйвер раз в секунду.
  - Ежедневный: 03 → 07 при ≥ 15 %, → 0f при ≥ 50 % (два замера); 0f → 07 после 15 с, 07 → 03 после 30 с.
  - Тестовая база (`lab_gov_nv`): форма NVIDIA, пороги 50 / 15 / 5 %.
  - Загрузку памяти наш регулятор не учитывает.
  - Тепловой тормоз 90 / 95 °C — наш. Аппаратные пороги в железе с загрузки: T2 102 °C, CRIT 104 °C.
- **Общность.** Логика регулятора — драйвер NVIDIA, вероятно **Fermi**. Числа порогов — ?.

## 14. Открытый код NVIDIA для Tegra: та же схема тактов (дополнено 25.10, 23:40)

**Откуда.** Подсказка из плана соседнего чата: смотреть открытый код NVIDIA для Tegra. Взяты только открытые источники
под GPL, авторство NVIDIA:
- в nouveau, который лежит у нас: `nvkm/subdev/clk/gk20a.c`, `gk20a.h`, `gm20b.c` (Copyright NVIDIA 2014–2016; Kepler
  GK20A и Maxwell GM20B в SoC Tegra);
- в nvgpu L4T (`InES-HPMM/linux-l4t`, ветка `hdmi2csi/l4t-r24-1-dev-4K`): `gk20a/hw_trim_gk20a.h`,
  `gk20a/clk_gk20a.c` (Copyright NVIDIA 2012–2014). Копия для чтения — в рабочей папке сессии, в репозиторий не кладётся.

**Те же адреса и поля, что у нашего GF114** (имена NVIDIA, «TRIM» — так NVIDIA называет такты):

| Адрес | Имя у NVIDIA | Поля | Что мы знали |
|---|---|---|---|
| 0x137000 | TRIM_SYS_GPCPLL_CFG | 0 ENABLE, 1 IDDQ, 2 SYNC_MODE (gm20b), 4 ENB_LCKDET (выкл. обнаружения захвата), 17 PLL_LOCK | то же: бит 2 — «синхронный режим», 17 — захват, бит 4 NVIDIA не ставит |
| 0x137004 | TRIM_SYS_GPCPLL_COEFF | M 0–7, N 8–15, PL 16–21 | то же (P << 16, N << 8, M) |
| 0x137100 | TRIM_SYS_SEL_VCO | бит 0 GPC2CLK_OUT: VCO (PLL) или BYPASS | наш «переключатель»; «bypass» у NVIDIA = наш путь делителя |
| 0x137250 | TRIM_SYS_GPC2CLK_OUT | BYPDIV 0–5 (делитель пути bypass), VCODIV 8–13 (делитель пути PLL), бит 31 SDIV14 | наш «пост-делитель»: поле 0–5 для пути делителя, 8–13 для пути PLL — совпало |
| 0x137340 | BYPASSCTRL_SYS (gm20b) | бит 0 GPCPLL: общий выбор bypass / VCO | у нас не читали |

**Правила в коде NVIDIA** (видно в открытом коде; это Kepler / Maxwell для Tegra, не Fermi):
1. Перед уходом с PLL на bypass — «разбить скачок пополам»: выходной делитель пути PLL ставится 1:2. Затем чтение,
   2 мкс выдержки и только потом запись в SEL_VCO. После возврата на PLL — снова 2 мкс и делитель обратно 1:1.
2. Делитель пишется **дважды**: «Intentional 2nd write to assure linear divider operation» — «второй намеренный запуск,
   чтобы делитель работал линейно».
3. «Put PLL in bypass before disabling it» — PLL выключают только после того, как узел ушёл с него.
4. SYNC_MODE ставят перед возвратом с bypass на PLL («для переключения без сбоя»), снимают перед выключением PLL.
5. Смена только выходного делителя PLL «без сбоя» — если у старого и нового значения есть общий единичный бит; иначе
   через промежуточное значение.

**Что это даёт карте:**
- **Имена и поля наших регистров подтверждены** открытым кодом NVIDIA (**видно**). Совпадение адресов у Fermi, Kepler и
  Maxwell говорит, что это один блок, переходящий из поколения в поколение (**гипотеза**). Значит, понимание Fermi
  переносимо дальше — в духе плана соседнего чата.
- **Правило 1** — то же, что мы видели в трассах GF114: «405 перед PLL», пост-делитель до переключателя (раздел 4.1). На
  GF114 NVIDIA уменьшает скачок через путь делителя, а не через делитель PLL — по нашим записям поле 8–13 там не меняется.
- **2 мкс между делителем и переключателем** — ровно то, что видно в трассе GF114 на спуске (делитель за ~2 мкс до
  переключателя). Вероятно, это одна и та же привычка драйвера (**гипотеза**). Наша команда пишет делитель вплотную к
  переключателю, без паузы, и всё равно лечит. Для патча в upstream пауза 2 мкс — кандидат «как у NVIDIA».
- **Правило 2 — новая зацепка для раздела 4.** NVIDIA сама пишет, что делитель после одной записи может делить
  неправильно. Это перекликается с «залежалой целью»: у делителя есть внутреннее состояние, которое запись приводит в
  порядок. Проверка — опыт Е9.
- **Правило 3 — ровно ошибка nouveau № 1** (раздел 8): после тайм-аута nouveau выключает PLL, на котором узел ещё стоит.
- **Бит 4 PLL.** У NVIDIA это выключение обнаружения захвата. У нас с этим битом после захвата ядро шло на ~25 МГц (ошибка
  nouveau № 5). Как одно связано с другим, не знаем — сверить при случае.
- **Пределы.** Это Tegra (без видеопамяти, со своим питанием) и другие поколения. На GF114 опираться на это можно только
  после своей проверки регистрами и трассой.

### 14.2. Имена NVIDIA для нашего теплового блока (28.10, hw_therm_gk20a.h / gm20b, класс Г)
Открытый код NVIDIA для Tegra (Kepler GK20A, Maxwell GM20B) называет регистры PTHERM так, и адреса совпадают с нашими:
| адрес | имя у NVIDIA | поля | что это у нас |
|---|---|---|---|
| 0x020130 | therm_config2 | бит 31 grad_enable («плавное замедление»), бит 24 slowdown_factor_extended (расширенный код коэффициента) | 8107040a у GF114/GF110, 8107030a у GF106/GF116: оба бита стоят у всех; драйвер читает его в каждой скобке (по 8 раз на переход у 390 и 270) — видимо, чтобы знать формат кода |
| 0x020160 + 4·i | therm_clk_slowdown[i] | биты 16–21 idle_factor, код = 2·делитель − 2: 1 = /1.5, 2 = /2, 6 = /4, 0xe = /8 | **наша скобка FSRM_2**: i = 0 — GPC, 1 — hub; код 0xa008a → idle_factor 0xa = **/6** (GPC на 1/6 — ровно что мы видели), 0x20082 → 0x2 = **/2**; у GF106 драйвер ставит GPC /2 |
| 0x0202c0 / 0x0202c4 | grad_stepping0 (бит 0 — включено) / grad_stepping1 (биты 0–16 — длительность шага) | плавный спуск коэффициента ступенями | **кандидат на физику выдержки П4**: если плавное замедление включено, коэффициент приходит ступенями, и время до полного замедления = число ступеней × длительность; признак в 0x0201e0 может означать начало, а не конец |
| 0x0202c8 + 4·i | grad_stepping_table[i] | пять 6-битных коэффициентов (nvgpu ставит /1.5, /2, /4, /8, /8) | ступени спуска |
| 0x0203c0 + 4·i | clk_timing[i] | бит 16 grad_slowdown | включение плавности по тактовому домену |
| 0x020200 + 4·i | gate_ctrl[i] | — | отключение тактов блоков (энергосбережение) |
Ни один драйвер в наших записях (390 на GF114 и GF106, 270.41.06) эти 0x0202xx/0x0203xx не пишет; devinit наших VBIOS — тоже
(GF106: только нули в 0x020210/214). Значит, плавность и длительность шага — состояние после POST / по умолчанию чипа;
прочитать их на нашей карте — `lab/therm-grad-probe.sh` (только чтение). Отсюда два следствия для модели: (1) «коэффициент
замедления» в скобке — выбор драйвера по чипу (/6 у GF114, /2 у GF106), а не свойство чипа; (2) выдержка П4, возможно,
равна времени плавного спуска, и тогда её можно вычислить из 0x0202c4, а не мерить. Кандидат-опыт Е14: тот же сценарий с
кодом GPC /2 (0x20082) и /8 (0xe008e) вместо /6 — меняется ли частота застреваний и нужная выдержка.
**Проба 28.10 (lab/therm-grad-probe.sh, наша карта, под лабораторным драйвером, класс Б):** config2 = 8107040a (grad_enable = 1,
extended = 1, байты 0x07/0x04/0x0a), clk_slowdown[0..3] = 0 / 82 / 80 / 80 (idle_factor 0 везде — скобка снята), статусы
0x0201e0/e4 = ff00, **grad_stepping0 = 0 (выключено), grad_stepping1 = 0 (длительность 0), таблица ступеней 0x0202c8… = 0,
clk_timing 0x0203c0… = 0**, gate_ctrl 0x020200… = 27722444 ×4. Итог: на GF114 регистры плавного замедления из кода Tegra
нулевые — либо на Fermi их нет, либо выключены; в любом случае гипотеза «выдержка П4 = время ступенчатого спуска»
**не подтверждается**: замедление в скобке включается сразу, и физика 2,2 → 4 мкс остаётся открытой (следующие кандидаты:
собственное время делителя/переключателя домена, Е14 с /2 и /8). Бит 31 config2 на Fermi, видимо, значит не то, что у
Kepler, или относится к другому механизму — имя из gk20a переносить осторожно.
**Проба 28.10 19:36 (lab/pll-ramp-probe.sh, по уровням 07 → 0f → 07 → 03, только чтение).** Регистры, которыми на
Kepler/Maxwell делают ramp PLL и DVFS (0x13700c CFG2, 0x137018 CFG3, 0x13701c NDIV_SLOWDOWN, 0x137010/14 DVFS0/1,
0x1328a0), на GF114 читаются **нулями на всех уровнях**, тогда как настоящие регистры PLL рядом меняются как положено
(CFG 00010000 → 00030005 на 0f, SEL_VCO 0 → 0x187). 0x137340 (BYPASSCTRL_SYS у gm20b, бит 0 = bypass) читается **1 на всех
уровнях, включая 0f**, где GPC стоит на PLL, — то есть это не живой бит bypass, как у Maxwell. Вывод (класс Б, чтение):
признаков механизма плавного замедления PLL на GF114 нет; доказать отсутствие чтением нельзя, но и повода для Е15
(запись в NDIV_SLOWDOWN) эти данные не дают — ни один из адресов не ведёт себя как регистр. Формулировка остаётся:
драйверы его не используют, а в железе он, по чтению, не виден.
**Скан корпуса VBIOS 28.10 (306 образов GF114/GF106/GF116/GF110, lab/vbios-devinit.py --corpus, класс В).** Ни один
скрипт devinit не пишет регистры плавного замедления ни из одного кандидата: 0x13700c–0x137020 (CFG2/CFG3/DVFS/NDIV_SLOWDOWN),
0x0202c0–0x0202dc (grad_stepping), 0x0203c0–0x0203d0 (clk_timing), 0x1328a0. Единственная запись в этой области —
0x137340 (nv_reg, маска ffffff78, скрипт 0, условие 11): **1 на GF114 (138 образов) и GF116 (88), 0 на GF106 (71) и
GF110 (8)**; дамп rox4d это подтверждает (= 0). У gm20b (nouveau, код NVIDIA) это BYPASSCTRL_SYS, бит 0 = bypass, при
инициализации ставится 0 («VCO»); на GF114 бит читается 1 на всех уровнях, включая 0f с GPC на PLL (проба 19:36), то есть
на Fermi он либо значит другое, либо это статическая настройка POST по чипу. Итог: чужие VBIOS к вопросу плавного
замедления ничего не добавляют — механизм не настраивается из VBIOS ни на одном Fermi; единственный след — чип-зависимый
бит 0x137340. Кандидат-опыт Е16 (на потом, только с контрольным шагом в той же сессии): записать в 0x137340 бит 0 = 0,
