# Генератор скриптов памяти, этап 2 (28.10): скрипты из VBIOS любой платы и проверка на чужом железе

## 1. Что сделано
`lab/memgen2.py` собирает пять скриптов памяти (A 03→07, B 07→0f, C 0f→07, D 07→07, E 07→03) для платы по её образу VBIOS
и индексу ramcfg (ремешок памяти: биты 2–5 регистра 0x101000, переведённые таблицей M0203 из BIT M, как в nouveau):
- скелет — порядок операций и записей из наших скриптов (запись NVIDIA на GF114; разметка этапа 1, `lab/memgen.py`);
- формулы (74 + 14 кандидатов) — из таблиц VBIOS платы (rammap, ramcfg ремешка, тайминги; сценарий BIT P+0x1c);
- «база платы» (44 записи) — состояние после POST по devinit VBIOS платы (симуляция записей скриптов инициализации с
  масками, `lab/vbios-devinit.py`) плюс управляющие биты шага по скелету;
- биты формульных регистров вне маски формулы — тоже из devinit платы, но только для тех регистров, где на нашей плате
  devinit совпал с записью (45 записей); где драйвер NVIDIA ставит их сам при загрузке (47 записей: 0x10f300, 0x10f604,
  0x10f610/614, 0x100c00, 0x00e108, 0x1373ec бит 16…), база остаётся нашей — это «состояние после инициализации драйвера»,
  в VBIOS его нет;
- коэффициенты MPLL — пересчёт под частоту 0f платы при опоре REFPLL из её devinit.
`lab/trace-memscr.py` достаёт скрипты памяти из любой записи mmiotrace (загрузки в память PMU через порт 0x10a1c0/0x10a1c4);
`lab/memgen2-compare.py` сверяет собранное с извлечённым по выравниванию последовательностей регистров.

## 2. Проверки
- **Самопроверка** (наша VBIOS, ремешок 3): все 314 записей пяти скриптов совпали с записью NVIDIA побайтно (0 отличий).
  Попутно найден бит 30 регистра 0x10f808: ставит драйвер перед скриптами, в devinit его нет (добавлен к управляющим).
- **Извлечение из записи** проверено на нашей записи t2: найденные загрузки совпали с массивами lab_nv_scrA/B один в один.
- **Корпус** (297 плат): скрипты собираются для 133 из 138 GF114 (5 плат без уровня 03 — нет скрипта E, так и должно
  быть), 71/71 GF106, 23/23 GF116 Rev. 2, 64/65 GTX 550 Ti; у GF106/GF116 нет записи 0x113644 в сценарии 0x1c (у них
  меньше разделов памяти — скелет GF114 здесь «шире» чипа).
- **Чужое железо, карта rox4d (GF106).** Его VBIOS у нас нет; взят образ той же версии и вендора из корпуса
  (Gigabyte GTS 450, 70.06.13.00.01, subsystem 1458:3500), ремешок из его записи: сырой 11 → индекс 3. Из его записи
  извлечены 14 загрузок скриптов (четыре разных: 81, 75–79, 56 и 45 записей; подъём 03→0f у него одним скриптом).
  Итог сверки по уникальным скриптам: последовательности регистров совпадают на 74–85 %; на общих регистрах значения
  совпали **248 из 283 (88 %)**; у него есть 53 записи, которых нет у нас, у нас 66, которых нет у него.

- **28.10, его настоящий VBIOS.** rox4d прислал дамп ROM своей карты; он побайтово равен образу TechPowerUp
  Gigabyte.GTS450.1024.100923.rom, по которому шла проверка выше. Генерация повторена по его файлу (ремешок 3):
  те же числа — 283 общих регистра, 248 совпали (88 %), 35 разошлись; только у него 53, только у нас 66
  (results/other-cards/gf106-rox4d/round3/). Проверка «двойником» была проверкой по настоящему VBIOS; оставшиеся
  расхождения (§3) к VBIOS не относятся.

## 3. Что именно расходится и почему (по меткам)
| группа | примеры | природа |
|---|---|---|
| адреса и состав по чипу | у него 0x13d874, у нас 0x13d8f4 (одна и та же роль перед операцией 0x3a); у нас 0x100760/764/768 (только GF114, «chipset 0xce» у Сплита), 0x110644/0x113644 — у него 0x111640/0x112640 (разделы памяти); у него 0x10f9b0/b4 | **скелет зависит от чипа**: порядок тот же, набор регистров и их адреса — по чипу |
| биты управления PLL по чипу | 0x10fe20 бит 17 (0x20030000 против 0x20010000), 0x132000 бит 16 | константы чипа в скелете |
| опора и коэффициенты MPLL | его 0x132004 = N 35 / M 11 при опоре 567 МГц (REFPLL 405·7/5, которую его скрипт не перепрограммирует: записи 0x10fe24 у него нет) | опора REFPLL после POST — из devinit его настоящей VBIOS; у нас 594 и перепрограммирование в скрипте — по чипу |
| биты «после инициализации драйвера» | 0x10f610/614 бит 29–30, 0x100c00, 0x00e108, 0x10f808 база, 0x1373ec 0x0303 | состояние, которое ставит драйвер при загрузке, по чипу/плате; в VBIOS нет |
| тайминги | 0x10f29c биты 25/29, 0x10f300 младшие биты, 0x10f330 | биты вне наших формул; часть, возможно, из его таблиц (образ не его) |

## 4. Что это значит и что нужно
Для драйвера семейства: формулы и таблицы VBIOS переносятся (на чужом GF106 88 % значений на общих регистрах совпали
без единой правки формул), а **скелет и «состояние после инициализации» — по чипу**: для GF106 их надо снять с записи
NVIDIA на GF106 так же, как мы сняли для GF114 (запись rox4d для этого уже достаточна: `lab/trace-memscr.py` даёт его
скрипты, разметка этапа 1 по его VBIOS даст его скелет). Нужны от rox4d: его образ VBIOS (`cat /sys/bus/pci/devices/…/rom`
после `echo 1 > rom`, 64 КБ) — тогда сверка станет точной, а не по образу-двойнику; и опционально запись с тремя переходами
памяти по отдельности (у него 03→0f одним скриптом). Для nouveau: генератор уже можно оформить как таблица «скелет по чипу»
+ формулы + devinit-база — это и есть то, что можно отправить, когда появится второй скелет.
