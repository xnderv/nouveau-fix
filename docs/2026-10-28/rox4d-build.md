# Сборка лабораторного драйвера для карты rox4d (GF106, GTS 450) — 28.10.2026

## 1. Замысел
rox4d прислал две записи mmiotrace драйвера NVIDIA 390.157 со своей карты и дамп её VBIOS. Повторить на его карте то,
что мы делаем на своей: ядро переключать кодом nouveau со скобкой FSRM (код замедлителя /2, как в его записи), память —
повтором скриптов PMU и прямых записей хоста **из его же записи** (класс Д, его карта), а не наших. Генератор по VBIOS
(memgen-stage2.md) даёт 88 % его регистров и тут не нужен: у нас есть его настоящие скрипты.

## 2. Данные и инструменты
- Скрипты PMU с сырыми словами: `lab/trace-memscr.py` теперь сохраняет `words` (BAR0 его карты 0xfc000000, наша 0xf4000000).
  У него 14 загрузок, 5 разных скриптов + вариант: **Bboot** (271 слово, с POST), **B** (271, те же, но три значения
  состояния: 0x132000 18000101→18010101, 0x1373ec, 0x137310 0808→1608), **C1** (257, первый спуск после Bboot), **C** (265,
  +0x137310=89200808 ×2, 0x10f628/0x10f62c), **E1** (189) и **E2** (164) — спуск 324→135 у него двумя скриптами подряд.
  Шага A (135→324) в его записи нет: NVIDIA на его карте поднимается с 135 сразу на 1804 одним скриптом B.
- Прямые записи хоста вокруг скриптов: `lab/trace-memhost.py` — правило отреза: pre = записи в регистры памяти за 20 мс до
  загрузки скрипта (после пуска предыдущего), post = после пуска (запись 0x10a4a0) до загрузки следующего, до первой записи
  в 0x100bxx или до 50 мс. **Проверено на нашей записи 20.10: воспроизводит все шесть массивов драйвера (preA 494 пар,
  midAB, postB, preC, midCD, postD) один в один.** У него: preBboot 494 пар (тот же блок обучающих шаблонов, что наш preA,
  значения свои: b2b2b2b2/4d4d4d4d против 9a9a9a9a/65656565), preB 14, postB 8, preC 7, postC 17, preE1 12, midE1E2 21,
  postE2 16. Группа 0x10f468/420/430/400/410/444 = 1005/42/40/1707/307/4cc001f — одинакова на обеих картах; 0x10f824
  (7fd4 / 7e77 / 79f7) и 0x132000 — свои.
- Окно записи для глаз: `lab/trace-window.py`.
- **Состояние памяти по 0x132000** (из его записи): 18010002 после POST (память 324 МГц — у GF106 POST оставляет 324, не
  135: 0x137310 = 81200808), 18000101 после Bboot, 18010101 после B, 18030000 после C/C1, 18010000 после E2. Текущую частоту
  узнаём как раньше: 0x1373f0 бит 1 → верх (1804), иначе 3240 / (поле 0x137310 + 2).
- **Напряжение (lab/vbios-vid.py, новый инструмент):** по таблице GPIO из DCB (линии VID0..4 = 17, 2, 5, 6, 7 — одинаковы
  на обеих платах) и записям NVIDIA в 0xe104/0xe280: у него 0f = VID 0x08 = **1,1125 В**, 03/07 = VID 0x14 = **0,9625 В**;
  у нас 0f = VID 0x0b = **1,075 В**, 03/07 = VID 0x15 = **0,95 В** — ровно то, что ставит наш драйвер по таблице VBIOS.
  Так закрыт «единственный непроверенный пункт» review-driver.md §8 (0xe104 — это VID, и наши напряжения совпадают с NVIDIA).
  Для его карты nouveau вычислит 0f по CVB и speedo чипа (диапазон 1,000–1,1375 В), значение заранее неизвестно, поэтому
  порог lab_volt_min_uv = 1112500 (см. ниже).

## 3. Что изменено в драйвере (lab/0002, собрано заново из дерева сборки)
- `fb/ramgf100.c`: таблицы GF106 (6 скриптов, 8 списков host); `struct lab_board` — плата = чип + PCI subsystem + уровни
  памяти + свои шаги + своя функция плана; `lab_boards[]`: GF114 1458:3515 (наша, 135/324/2004, план как был) и
  GF106 1458:3500 (rox4d, 135/324/1804). Плата определяется в `gf100_ram_new_`; **чужая плата → повтор скриптов памяти
  отказывает** (-ENODEV, ядро можно переключать с lab_mem=0). План GF106 по 0x132000: с 1804 → C1 или C (+E1,E2 до 135);
  с 324 после POST → только Bboot на 1804 (иначе отказ: других переходов из этого состояния в записи нет); с 324 после C →
  E1,E2 (+B до 1804); с 135 → B (+C до 324). Переходы 324→1804 (кроме Bboot) и 135→324 в записи отсутствуют — идём
  известными шагами через 135 / через 1804 (отклонение от NVIDIA только в паузах между шагами).
  Биты lab_mem_replay: 2 — подъём на 1804, 4 — спуск с 1804, 8 — E1+E2; бит 1 (A) на GF106 не нужен → **14**.
- `clk/gf100.c`: `lab_therm_gpc_factor` по умолчанию 0 = по чипу (GF114 0xa = /6, GF106 0x2 = /2; явное значение
  по-прежнему можно задать — Е14).
- `volt/base.c`: `lab_volt_min_uv` теперь порог только для вычисляемых (CVB) записей карты напряжений, то есть для 0f;
  03/07 остаются табличными; потолок по чипу = значение NVIDIA на 0f (GF114 1 075 000, GF106 1 112 500 мкВ).
- На нашей карте поведение не меняется: та же плата, те же шаги; `lab_therm_gpc_factor=0` даёт 0xa; `lab_volt_min_uv=0`
  в base() — порог выключен.
- Патч проверен: `git apply --check` на базу v7.0 и `patch --dry-run` на nouveau из **ядра 6.18** (частичный клон
  torvalds/linux v6.18) — без конфликтов; 0001, 0004, 0006 тоже ложатся (0001 со сдвигами строк).

## 4. Сборка у rox4d (Debian, своё ядро 6.18.58+)
Патчи: `patches/0001-…abi16…`, `lab/0002-LAB-fermi-reclock-instrumented.patch`, `patches/0004-LAB-pmu-perf-load.patch`
(прошивка PMU — заголовок уже пересобран), `patches/0006-…therm-mask-pwm…` (без него вентилятор читается как 0 % и
поднимается по 3 %). В дереве его ядра (собранном, с его .config): `cd drivers/gpu/drm/nouveau && patch -p1 < …` ×4,
затем `make -j$(nproc) M=drivers/gpu/drm/nouveau modules`, подменить nouveau.ko (резервная копия, depmod, initramfs,
если nouveau в нём). Нужен CONFIG_DRM_NOUVEAU=m. Ключи (всё остальное — значения по умолчанию = наш base()):
`options nouveau lab_mem_replay=14 lab_volt_min_uv=1112500 lab_pcie=0 lab_clk_mmu_lock=0 lab_gpc_div=1 lab_pmu_div=1`.
Делитель PMU 0x137280 NVIDIA ни на одной карте не пишет — стоит с POST 0e0e (202,5 МГц), lab_pmu_div=1 даёт то же.

## 5. Протокол: `lab/rox4d-test.sh`
Проверяет, что модуль узнал плату (строка «LAB: плата GF106…» в dmesg), печатает ключи, затем 0f → 07 → 03 циклами
с паузами, после каждого шага — строки LAB из dmesg и ошибки; стоп на первой ошибке; в конце полный dmesg. **Первый
переход после загрузки — только на 0f** (единственный переход из состояния после POST, который есть в записи).

## 6. Риски и честная оценка (сказать ему прямо)
- Зависания и жёсткие сбросы — вероятны при первых попытках; несохранённые данные; артефакты изображения в момент перехода.
- Повода ждать повреждения железа нет: частоты и напряжения — уровни его VBIOS и значения, которые на его карте ставил
  драйвер NVIDIA (напряжение 0f не выше 1,1125 В — потолок в коде); на другой плате память не трогается. Но гарантий нет.
- Что не покрыто: блок 0x100bxx после переходов (как и у нас — пропущен, драйвер работает без него); записи GPIO 0xe104
  пропускаются (напряжение ставит nouveau по VBIOS; порог 0f); температурная часть CVB; speedo; маршруты через 135/1804.
- Шансы: ядро — высокие (на других Fermi у Twilight0 работает; скобка с кодом /2 из его записи); память на первой
  попытке — ниже 50 %; любой исход даёт данные класса Д по чужому чипу.
